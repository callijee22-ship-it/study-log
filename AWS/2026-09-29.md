# 🔍 Amazon Athena

Athena는 S3에 저장된 데이터를  
SQL을 이용해서 직접 조회할 수 있는 Serverless 분석 서비스이다.

별도의 서버나 데이터베이스를 직접 구성하지 않아도  
S3 데이터를 SQL로 조회할 수 있다.

### 내가 이해한 방식

```text
S3
 ↓
Athena
 ↓
SQL Query
```

### ⭐ 기억하기

```text
Athena = S3 데이터를 SQL로 조회
```

---

# 🏢 Amazon Redshift Spectrum

Redshift Spectrum도  
S3에 저장된 데이터를 조회할 수 있다.

하지만 Athena와 달리  
**Redshift 환경에서 S3의 외부 데이터를 조회할 때 사용**한다.

### 내가 이해한 방식

```text
Redshift
   ↓
Spectrum
   ↓
S3 데이터 조회
```

### ⭐ 기억하기

```text
Redshift Spectrum
= Redshift에서 S3 조회
```

---

# 🤔 Athena vs Redshift Spectrum

오늘 문제에서 특히 헷갈렸던 부분이다.

둘 다 S3 데이터를 SQL로 조회할 수 있어서  
처음에는 비슷하게 느껴졌다.

## Athena

```text
S3
 ↓
SQL 조회
```

- Serverless
- S3 데이터를 직접 분석
- 별도의 Redshift가 필요하지 않음

### 기억하기

```text
S3를 바로 SQL로 조회
→ Athena
```

---

## Redshift Spectrum

```text
Redshift
    ↓
Spectrum
    ↓
S3
```

- Redshift와 함께 사용
- Redshift에서 외부 S3 데이터를 조회

### 기억하기

```text
Redshift에서 S3 조회
→ Redshift Spectrum
```

---

## ⭐ 한 번에 구분하기

```text
S3 + SQL
→ Athena

Redshift + S3
→ Redshift Spectrum
```

---

# 🧹 AWS Glue

Glue는 데이터를  
분석하기 좋은 형태로 정리하고 변환하는 데 사용하는 서비스이다.

ETL 작업에 사용할 수 있으며  
Serverless 방식으로 사용할 수 있다는 점을 다시 복습했다.

```text
데이터
 ↓
Glue
 ↓
ETL / 변환
 ↓
정리된 데이터
```

### ⭐ 기억하기

```text
Glue = Serverless ETL
```

---

# 🐘 Amazon EMR

EMR은 Spark, Hadoop과 같은  
빅데이터 기술을 이용해서 대규모 데이터를 처리할 때 사용할 수 있다.

Glue와 달리  
클러스터 환경을 직접 다루고 제어해야 하는 상황에서 사용할 수 있다.

### 내가 이해한 방식

```text
대규모 데이터
      ↓
Spark / Hadoop
      ↓
EMR
```

### ⭐ 기억하기

```text
EMR = Spark / Hadoop 기반 빅데이터 처리
```

---

# 🤔 Glue vs EMR

오늘 반복해서 틀리고 다시 잡았던 부분이다.

## Glue

```text
Serverless
+
ETL
+
관리 부담 적음
```

### 기억하기

```text
Serverless ETL
→ Glue
```

---

## EMR

```text
Spark / Hadoop
+
대규모 분산 처리
+
클러스터 제어
```

### 기억하기

```text
직접 클러스터를 제어하며
Spark / Hadoop 사용
→ EMR
```

---

## ⭐ 한 번에 구분하기

```text
쉽게 ETL
→ Glue

Spark / Hadoop + 클러스터 제어
→ EMR
```

---

# 🕷️ Glue Crawler

Glue Crawler는 데이터 소스를 확인해서  
Schema를 자동으로 찾아주는 기능이다.

예를 들어 S3에 데이터가 있다면:

```text
S3
 ↓
Glue Crawler
 ↓
Schema 발견
 ↓
Data Catalog
```

### ⭐ 기억하기

```text
Crawler = 데이터 구조 자동 탐색
```

---

# 📚 Glue Data Catalog

Data Catalog는  
Crawler 등이 찾아낸 데이터의 구조 정보를 저장한다.

실제 데이터 자체가 아니라

- Table
- Column
- Data Type
- Schema

같은 **Metadata**를 관리한다고 이해했다.

### ⭐ 기억하기

```text
Data Catalog = Metadata 저장
```

---

# 🔗 Crawler → Catalog → Athena

오늘 중요한 흐름 중 하나였다.

```text
S3 데이터
   ↓
Glue Crawler
   ↓
Schema 탐색
   ↓
Glue Data Catalog
   ↓
Metadata 등록
   ↓
Athena
   ↓
SQL Query
```

### 내가 이해한 방식

```text
Crawler
= 데이터 구조 찾기

Catalog
= 구조 정보 저장

Athena
= SQL로 조회
```

### ⭐ 한 줄 암기

```text
찾기 → 저장 → 조회
Crawler → Catalog → Athena
```

---

# 📄 Parquet

Parquet은 데이터를 저장하는 파일 형식 중 하나이다.

특히 분석할 때 필요한 Column만 읽을 수 있어서  
불필요한 데이터 스캔을 줄일 수 있다.

### 내가 이해한 방식

```text
전체 데이터를 다 읽지 않고
필요한 Column 중심으로 읽기
```

Athena처럼  
스캔한 데이터 양이 비용에 영향을 줄 수 있는 환경에서는  
Parquet을 사용하면 비용과 성능 측면에서 도움이 될 수 있다.

### ⭐ 기억하기

```text
Parquet
= Columnar Format
= 필요한 Column 중심으로 읽기
= Scan 감소
```

---

# 📂 Partitioning

Partitioning은 데이터를 특정 기준으로 나누어서 저장하는 방식이다.

예를 들어 날짜 기준으로 나눈다면:

```text
data/
├── year=2026/
│   ├── month=09/
│   │   ├── day=28/
│   │   └── day=29/
```

필요한 날짜의 데이터만 조회할 수 있기 때문에  
전체 데이터를 전부 스캔하지 않아도 된다.

### ⭐ 기억하기

```text
Partitioning
= 데이터를 조건별로 나누어 저장
```

---

# 💰 Athena 비용 줄이기

오늘 Parquet과 Partitioning을 함께 공부한 이유이다.

Athena는 Query를 실행할 때  
스캔하는 데이터 양이 중요하다.

그래서:

```text
Parquet
+
Partitioning
        ↓
불필요한 Scan 감소
        ↓
Athena 비용 감소
```

### ⭐ 기억하기

```text
Athena 비용 절감
→ Parquet + Partitioning
```

# 🧊 S3 Storage Class 복습

오늘은 데이터 분석 서비스뿐 아니라  
이전에 공부했던 S3 Storage Class도 문제로 다시 복습했다.

특히 다음 개념을 다시 구분했다.

- Intelligent-Tiering
- Lifecycle
- Standard-IA
- Glacier Flexible Retrieval
- Glacier Deep Archive

---

# 🔄 Intelligent-Tiering vs Lifecycle

이 둘은 계속 헷갈렸던 부분이다.

## Intelligent-Tiering

데이터의 접근 패턴을 예측하기 어려울 때  
AWS가 접근 패턴을 보고 적절한 Tier로 관리한다.

```text
접근 패턴을 모름
→ Intelligent-Tiering
```

---

## Lifecycle

사용자가 직접 규칙을 설정한다.

예:

```text
30일 후 Standard-IA
90일 후 Glacier
```

### ⭐ 구분하기

```text
AWS가 접근 패턴을 보고 관리
→ Intelligent-Tiering

내가 날짜와 규칙을 설정
→ Lifecycle
```

---

# 📦 Standard-IA

자주 접근하지 않는 데이터이지만  
필요할 때는 빠르게 접근해야 하는 경우 사용한다.

### ⭐ 기억하기

```text
Standard-IA
= Infrequent Access
= 자주 사용하지 않지만 즉시 접근
```

---

# 🧊 Glacier Flexible Retrieval

장기간 보관하면서  
필요한 경우 데이터를 다시 복원해야 할 때 사용할 수 있다.

복구에는 즉시 접근보다는 시간이 걸릴 수 있다.

### ⭐ 기억하기

```text
Flexible Retrieval
= 장기 보관
+ 필요하면 복원
+ 복원에 시간이 걸릴 수 있음
```

---

# 🧊 Glacier Deep Archive

매우 장기간 보관하고  
거의 접근하지 않는 데이터를 위한 저장 클래스이다.

### ⭐ 기억하기

```text
Deep Archive
= 초장기 보관
+ 거의 접근 안 함
+ 낮은 저장 비용
```

# 🔥 실제 오답 기록과 다시 잡은 개념

이날은 단순히 비슷한 서비스를 비교한 것뿐 아니라  
실제로 문제를 풀다가 잘못 고른 답이 있었다.

정답만 남기면 나중에 왜 헷갈렸는지 사라지기 때문에  
오답 선택과 다시 잡은 기준을 같이 기록한다.

## 1. Athena vs Redshift Spectrum

문제 상황:

```text
이미 Redshift를 사용 중
+
S3 데이터를 Redshift로 복사하지 않고 조회
```

처음 선택:

```text
1번 Athena ❌
```

다시 확인한 정답:

```text
2번 Redshift Spectrum ✅
```

처음에는

```text
"S3를 SQL로 조회"
→ Athena
```

만 떠올려서 Athena를 선택했다.

하지만 문제에는 이미 **Redshift를 사용 중**이라는 조건이 있었다.

다시 구분:

```text
Redshift 없이 S3를 바로 SQL로 조회
→ Athena

이미 Redshift를 사용하면서
S3 외부 데이터를 조회
→ Redshift Spectrum
```

### 이해 상태

```text
처음
→ Athena와 Spectrum을 "둘 다 S3 조회" 정도로 봄

재설명 후
→ Redshift가 이미 있느냐를 먼저 확인해야 한다는 기준을 잡음

상태
→ 구분 기준은 잡혔지만 반복 문제로 확인 필요
```

---

## 2. Intelligent-Tiering vs Lifecycle

문제 상황:

```text
데이터 접근 패턴을 예측하기 어려움
+
자동으로 적절한 Storage Tier 사용
```

처음 선택:

```text
3번 Lifecycle ❌
```

다시 확인한 정답:

```text
2번 Intelligent-Tiering ✅
```

처음에는 둘 다 Storage Class가 바뀔 수 있다는 점 때문에 헷갈렸다.

다시 구분:

```text
Intelligent-Tiering
→ 접근 패턴을 보고 AWS가 자동 관리

Lifecycle
→ 사용자가 날짜와 규칙을 직접 설정
```

예:

```text
"언제 자주 볼지 모르겠음"
→ Intelligent-Tiering

"30일 후 IA, 90일 후 Glacier"
→ Lifecycle
```

### 이해 상태

```text
처음
→ 자동 이동이라는 공통점 때문에 둘을 섞음

재설명 후
→ "AWS가 판단" vs "내가 규칙 설정"으로 구분

상태
→ 핵심 차이는 이해했지만 당시 반복해서 헷갈린 항목
```

---

## 3. Glue vs EMR

문제 상황:

```text
대규모 Spark ETL
+
서버리스
+
클러스터 관리 불필요
```

처음 선택:

```text
1번 EMR ❌
```

다시 확인한 정답:

```text
2번 AWS Glue ✅
```

처음에는 문제에 **Spark**가 보이자 EMR을 먼저 떠올렸다.

하지만 문제의 더 중요한 조건은:

```text
Serverless
클러스터 관리 불필요
ETL
```

이었다.

다시 구분:

```text
Glue
→ Serverless ETL
→ 클러스터 직접 관리 X

EMR
→ Spark / Hadoop 기반 대규모 처리
→ 클러스터 구성과 제어가 필요한 경우
```

### 이해 상태

```text
처음
```
