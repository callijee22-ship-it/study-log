# 1. Amazon Athena

Athena는 S3에 저장된 데이터를 SQL로 직접 조회할 수 있는 Serverless 분석 서비스다.

```text
S3
 ↓
Athena
 ↓
SQL Query
```

### 내가 이해한 방식

```text
Redshift 같은 별도 데이터웨어하우스 없이
S3를 바로 SQL로 조회
→ Athena
```

### 핵심

```text
Athena = S3 + SQL + Serverless
```

---

# 2. Amazon Redshift Spectrum

Redshift Spectrum도 S3 데이터를 조회할 수 있다.

하지만 핵심은 **이미 Redshift를 사용하고 있는 환경에서 S3 외부 데이터를 조회**하는 것이다.

```text
Redshift
   ↓
Spectrum
   ↓
S3 외부 데이터
```

### 핵심

```text
Redshift에서 S3 조회
→ Redshift Spectrum
```

---

# 3. Athena vs Redshift Spectrum

이 부분은 실제 문제에서 틀렸다.

문제 상황:

```text
이미 Redshift를 사용 중
+
S3 데이터를 Redshift로 복사하지 않고 바로 조회
```

처음 선택:

```text
1번 Athena ❌
```

정답:

```text
2번 Redshift Spectrum ✅
```

처음에는

```text
S3 + SQL
→ Athena
```

만 떠올렸다.

하지만 문제에 **이미 Redshift를 사용 중**이라는 조건이 있었다.

다시 구분:

```text
S3를 바로 SQL로 조회
→ Athena

Redshift 환경에서 S3 외부 데이터를 조회
→ Redshift Spectrum
```

### 이해 상태

```text
오답 전
→ 둘 다 S3 조회 서비스 정도로 봄

재설명 후
→ "이미 Redshift를 쓰는가?"를 먼저 보게 됨

상태
→ 구분 기준은 잡혔지만 반복 문제로 확인 필요
```

---

# 4. AWS Glue

Glue는 ETL 작업을 Serverless 방식으로 수행할 수 있는 서비스다.

```text
데이터
 ↓
Glue
 ↓
ETL / 변환
 ↓
정리된 데이터
```

### 핵심

```text
Glue = Serverless ETL
```

---

# 5. Amazon EMR

EMR은 Spark, Hadoop 같은 빅데이터 기술을 이용해 대규모 데이터를 처리할 때 사용하는 서비스다.

```text
대규모 데이터
      ↓
Spark / Hadoop
      ↓
EMR
```

### 핵심

```text
EMR
→ Spark / Hadoop
→ 대규모 분산 처리
→ 클러스터 환경 제어
```

---

# 6. Glue vs EMR

이 부분은 **정답은 맞혔지만 확신이 부족했다.**

문제 상황:

```text
대규모 Spark ETL
+
서버 관리 없이
+
클러스터 관리 없이
```

사용자 답:

```text
2번같은데
→ AWS Glue ✅
```

정답은 맞았지만 "2번같은데"라고 답할 정도로 확신이 부족했다.

중요했던 건 문제에 Spark가 보인다고 무조건 EMR을 고르는 게 아니었다는 점이다.

다시 구분:

```text
Glue
→ Serverless ETL
→ 클러스터 직접 관리 X

EMR
→ Spark / Hadoop 기반 대규모 처리
→ 클러스터 제어가 필요한 경우
```

### 이해 상태

```text
정답 여부
→ 맞음

개념 상태
→ 차이는 설명을 듣고 잡힘
→ 다만 문제에서 바로 확신 있게 고르는 수준은 아니었음
```

---

# 7. Glue Crawler

Glue Crawler는 데이터 소스를 확인해서 Schema를 자동으로 찾아준다.

```text
S3
 ↓
Glue Crawler
 ↓
Schema 탐색
 ↓
Data Catalog
```

### 핵심

```text
Crawler
→ 데이터 구조 자동 탐색
```

---

# 8. Glue Data Catalog

Data Catalog는 실제 데이터를 저장하는 것이 아니라 Metadata를 관리한다.

예:

```text
Table
Column
Data Type
Schema
```

### 핵심

```text
Data Catalog
→ Metadata 저장
```

---

# 9. Crawler vs Data Catalog

문제에서 한 번 1번을 눌렀지만 곧바로 **잘못 눌렀다고 정정**했다.

따라서 이건 개념 오답으로 기록하지 않는다.

다시 구분:

```text
Crawler
→ 구조를 찾음

Data Catalog
→ 찾은 구조 정보를 저장
```

연결:

```text
S3
 ↓
Crawler
 ↓
Schema 탐색
 ↓
Data Catalog
 ↓
Metadata 저장
 ↓
Athena
 ↓
SQL Query
```

### 이해 상태

```text
오답
→ 아님. 잘못 누른 입력

개념 상태
→ 역할 연결은 이해
```

---

# 10. Parquet

Parquet은 Columnar Format이다.

분석할 때 필요한 Column 중심으로 읽을 수 있어 불필요한 Scan을 줄이는 데 도움이 된다.

```text
Parquet
→ Columnar Format
→ 필요한 Column 중심으로 읽기
→ Scan 감소
```

Athena처럼 스캔한 데이터 양이 비용에 영향을 주는 환경에서 중요하다.

---

# 11. Partitioning

Partitioning은 데이터를 특정 기준으로 나누어 저장하는 방식이다.

예:

```text
data/
├── year=2026/
│   └── month=09/
│       ├── day=28/
│       └── day=29/
```

필요한 날짜 파티션만 조회하면 전체 데이터를 다 읽지 않아도 된다.

```text
Partitioning
→ 조건별로 데이터를 나눔
→ 불필요한 Scan 감소
```

---

# 12. Parquet + Partitioning

Athena 비용 절감과 연결해서 봤다.

```text
Parquet
+
Partitioning
        ↓
불필요한 Scan 감소
        ↓
Athena 비용 감소
```

### 이해 상태

```text
Parquet
→ Column 중심

Partitioning
→ 경로/조건 기준으로 데이터 범위를 줄임

둘의 목적
→ Scan 감소
```

이 연결은 이해한 상태였다.

---

# 13. S3 Intelligent-Tiering

데이터 접근 패턴을 예측하기 어려울 때 사용하는 Storage Class다.

AWS가 접근 패턴을 보고 적절한 Tier로 관리한다.

```text
접근 패턴 예측 어려움
→ Intelligent-Tiering
```

---

# 14. S3 Lifecycle

Lifecycle은 사용자가 직접 규칙을 설정한다.

예:

```text
30일 후 Standard-IA
90일 후 Glacier
```

### 핵심

```text
Lifecycle
→ 내가 날짜/규칙 설정
```

---

# 15. Intelligent-Tiering vs Lifecycle

이 부분은 실제 문제에서 틀렸다.

문제 상황:

```text
데이터 접근 패턴을 예측하기 어려움
+
자동으로 적절한 Storage Tier 사용
```

처음 선택:

```text
3번 Lifecycle ❌
```

정답:

```text
2번 Intelligent-Tiering ✅
```

처음에는 둘 다 Storage Class가 이동될 수 있다는 점 때문에 헷갈렸다.

다시 구분:

```text
Intelligent-Tiering
→ AWS가 접근 패턴을 보고 자동 관리

Lifecycle
→ 내가 규칙과 날짜를 직접 설정
```

### 이해 상태

```text
오답 전
→ 둘 다 "자동으로 Storage Class 이동" 정도로 섞임

재설명 후
→ AWS 판단 vs 사용자 규칙으로 구분

상태
→ 핵심 차이는 이해
→ 당시 반복해서 헷갈린 항목이므로 복습 필요
```

---

# 16. Standard-IA

자주 접근하지 않는 데이터지만 필요할 때 빠르게 접근해야 할 때 사용한다.

```text
Standard-IA
→ Infrequent Access
→ 자주 안 쓰지만 즉시 접근
```

---

# 17. Glacier Flexible Retrieval

장기 보관용이며 필요하면 복원할 수 있다.

복원은 즉시가 아니라 몇 분~몇 시간 정도 걸릴 수 있다.

```text
Flexible Retrieval
→ 장기 보관
→ 복원 가능
→ 몇 분~몇 시간
```

---

# 18. Glacier Deep Archive

매우 장기간 보관하고 거의 접근하지 않는 데이터에 적합하다.

```text
Deep Archive
→ 초장기 보관
→ 거의 접근 안 함
→ 복원 오래 걸림
```

---

# 19. Flexible Retrieval vs Deep Archive

이 부분도 답을 확신 있게 고른 상태는 아니었다.

사용자 답:

```text
2번?
```

다시 구분:

```text
Flexible Retrieval
→ 몇 분~몇 시간 정도의 복구

Deep Archive
→ 12시간 이상 기다려도 되는 초장기 보관
```

### 이해 상태

```text
정답 여부보다
→ 복구 시간 차이를 다시 확인한 것이 중요

상태
→ 구분은 다시 했지만 확신 부족 흔적이 있었음
```
