# 2. Kinesis Data Streams
## 실시간 Streaming Data(스트리밍 데이터) 처리

Amazon Kinesis Data Streams는  
실시간으로 계속 들어오는 데이터를 받아 처리할 때 사용하는 서비스다.

예:

~~~text
클릭 로그
애플리케이션 로그
센서 데이터
실시간 이벤트
~~~

개념 흐름:

~~~text
Producer(생산자)
→ Kinesis Data Streams
→ Consumer(소비자)
~~~

오늘은 Kinesis 자체보다  
Kinesis 안에서 자주 헷갈리는 기능들을 집중해서 봤다.

---

# 3. Enhanced Fan-Out
## 향상된 팬아웃

Enhanced Fan-Out은 여러 Consumer가 Kinesis 데이터를 읽을 때  
각 Consumer에게 전용 처리량을 제공하는 기능이다.

핵심:

~~~text
여러 Consumer가 동시에 읽음
→ 서로 처리량을 나눠 쓰지 않게 함
→ Consumer별 전용 Throughput(처리량)
~~~

기억:

~~~text
Consumer가 많다
+
각자 빠르게 읽어야 한다
→ Enhanced Fan-Out
~~~

---

# 4. Retention Period
## 데이터 보존 기간

Retention Period는 Kinesis에 들어온 데이터를  
얼마 동안 다시 읽을 수 있게 보관할지 정하는 기간이다.

예:

~~~text
Consumer 장애
→ 몇 시간 뒤 복구
→ 이전에 못 읽은 데이터 다시 읽기
~~~

이럴 때 필요한 것이:

~~~text
Retention Period
~~~

이다.

핵심:

~~~text
Retention
→ 보관
→ 나중에 다시 읽기
~~~

---

# 5. Enhanced Fan-Out vs Retention Period

둘은 문제에서 함께 나오면 헷갈릴 수 있다.

~~~text
Enhanced Fan-Out
→ Consumer 처리량 문제

Retention Period
→ 과거 데이터를 다시 읽는 문제
~~~

문제 키워드로 보면:

~~~text
Consumer 여러 개
전용 처리량
동시에 빠르게 읽기
→ Enhanced Fan-Out

장애 후 복구
지난 데이터 재처리
다시 읽기
→ Retention Period
~~~

### 이해 상태

아침에 배운 뒤  
밤 복습에서는 이 둘을 다시 맞혔다.

~~~text
Enhanced Fan-Out
→ 회수 성공

Retention Period
→ 회수 성공
~~~

# 6. Partition Key
## 파티션 키

Kinesis에서 어떤 Record(레코드)를  
어느 Shard(샤드)에 넣을지 결정하는 데 사용하는 값이다.

큰 그림:

~~~text
Record
→ Partition Key 확인
→ 특정 Shard로 분배
~~~

같은 Partition Key가 반복되면  
특정 Shard로 데이터가 몰릴 수 있다.

핵심:

~~~text
Partition Key
→ Shard 분배 기준
→ 순서 / 분산과 관련
~~~

---

# 7. Hot Shard
## 특정 Shard에 부하 집중

Hot Shard는 Kinesis에서  
특정 Shard에 데이터나 요청이 지나치게 몰리는 상태다.

예:

~~~text
Partition Key가 고르게 분산되지 않음
→ 특정 Shard에 Record 집중
→ 해당 Shard만 과부하
~~~

핵심:

~~~text
Kinesis
+
특정 Shard 과부하
→ Hot Shard
~~~

---

# 8. Glue Crawler
## 스키마 자동 탐색

AWS Glue Crawler는  
S3 등의 데이터 소스를 스캔해서 Schema(스키마 / 데이터 구조)를 찾아낸다.

예:

~~~text
S3 데이터
→ Glue Crawler
→ Column / Type 등 구조 파악
→ Data Catalog에 Metadata(메타데이터) 등록
~~~

핵심:

~~~text
Crawler
→ Schema 발견
→ Metadata 등록
~~~

---

# 9. Glue Schema Registry
## 스키마 버전 / 호환성 관리

Glue Schema Registry는  
Streaming Data(스트리밍 데이터)의 Schema를 등록하고  
Version(버전)과 Compatibility(호환성)를 관리하는 데 사용한다.

예:

~~~text
Producer가 보내는 Event 구조가 바뀜
→ Schema Version 관리
→ 기존 Consumer와 호환되는지 확인
~~~

핵심:

~~~text
Crawler
→ 데이터 구조를 찾아냄

Schema Registry
→ Schema 버전 / 호환성 관리
~~~

---

# 10. Crawler vs Schema Registry

~~~text
이미 있는 데이터 구조를 탐색
→ Glue Crawler

Streaming Schema 버전 / 호환성 관리
→ Glue Schema Registry
~~~

---

# 11. Data Skew
## 데이터 편향

Data Skew는 Glue / Spark 같은 분산 처리에서  
데이터가 Worker(작업 노드)들에게 고르게 나뉘지 않고  
일부 Worker에 몰리는 현상이다.

예:

~~~text
Worker A
→ 데이터 너무 많음

Worker B
→ 데이터 적음

Worker C
→ 데이터 적음
~~~

결과:

~~~text
Worker A만 오래 걸림
→ 전체 Job도 늦어짐
~~~

핵심:

~~~text
Glue / Spark
+
Worker별 데이터 불균형
→ Data Skew
~~~

---

# 12. Repartition
## 파티션 재분배

Repartition은 데이터를 다시 나누어  
Partition(파티션)을 재구성하는 작업이다.

Data Skew가 심한 상황에서  
데이터를 더 고르게 분배하는 데 사용할 수 있다.

큰 그림:

~~~text
데이터가 한쪽에 몰림
→ Repartition
→ 다시 분산
~~~

핵심:

~~~text
Repartition
→ 데이터 재분배
~~~

---

# 13. Hot Shard vs Data Skew

오늘 가장 중요한 혼동 포인트였다.

둘 다:

~~~text
"한쪽으로 몰린다"
~~~

는 공통점이 있어서 헷갈렸다.

하지만 발생 위치가 다르다.

## Hot Shard

~~~text
Kinesis
→ Shard에 데이터 집중
~~~

## Data Skew

~~~text
Glue / Spark
→ Worker에 데이터 집중
~~~

한 줄로:

~~~text
Kinesis Shard 문제
→ Hot Shard

Glue / Spark Worker 문제
→ Data Skew
~~~

# 14. Athena + Parquet + Partitioning
## 비교적 안정적으로 구분된 영역

오늘 문제에서 이 부분은 비교적 안정적으로 풀었다.

## Amazon Athena(아테나)

S3 데이터를 SQL로 직접 조회하는 Serverless Query Service(서버리스 쿼리 서비스).

~~~text
S3
→ Athena
→ SQL Query
~~~

## Parquet(파케이)

Columnar Format(열 지향 형식)이다.

필요한 Column 위주로 읽을 수 있어서  
분석 쿼리의 Scan(스캔) 양을 줄이는 데 유리하다.

## Partitioning(파티셔닝)

데이터를:

~~~text
날짜
지역
연도 / 월
~~~

같은 기준으로 나눠 저장하고  
필요한 Partition만 읽도록 하는 방식이다.

핵심 연결:

~~~text
Athena 비용 / 성능 개선
→ Scan 줄이기

Scan 줄이는 방법
→ Parquet
→ Partitioning
~~~

### 이해 상태

~~~text
Athena + Parquet + Partitioning
→ 오늘 문제에서는 비교적 안정적
~~~

문제에서 Glue / Spark Worker 불균형 상황을 보고

~~~text

~~~

다시 정리:

~~~text

→ Data Skew

Kinesis Shard 불균형
→ Hot Shard
~~~

### 현재 상태

~~~text

→ 회수됨

Enhanced Fan-Out
→ 회수됨
~~~
