# ☁️ 2026-10-07 AWS Study

## 📌 오늘의 기록

오늘은 AWS DEA-C01 문제를 계속 풀면서 새로운 개념을 많이 접했다.

중요한 점은 **정답을 맞혔다고 해서 이해가 끝난 것으로 기록하지 않는 것**이다.

오늘 기록은 아래 기준으로 남긴다.

~~~text
정답 + 이유까지 설명 가능
→ 비교적 회수됨

정답은 맞혔지만 망설임
→ 확신 부족 / 반복 필요

처음 보는 개념이거나 설명을 들은 뒤 이해
→ 새로 학습 / 재확인 필요

비슷한 서비스와 계속 섞임
→ 미정착
~~~

오늘 다룬 범위가 넓어서, 지금 단계에서는
**“한 번 본 개념을 다시 꺼내 볼 수 있도록 정리하는 복습 자료”**로 보는 것이 맞다.

# 1. Exponential Backoff(지수 백오프)

일시적인 오류가 났을 때 바로 계속 재시도하는 것이 아니라,
재시도 간격을 점점 늘리는 방식이다.

예:

~~~text
5초 후 재시도
→ 10초 후
→ 20초 후
→ 40초 후
~~~

이 방식은 서버나 API에 순간적인 부하가 몰리는 것을 줄이는 데 도움이 된다.

### 문제에서 볼 단서

~~~text
일시적 오류
재시도
간격 증가
Throttling(스로틀링)
~~~

### 오늘 상태

Q26, Q28 유형에서 정답을 골랐고,
재시도 간격이 늘어난다는 핵심은 다시 확인했다.

~~~text
Exponential Backoff
→ 재시도 간격 증가
~~~

---

# 2. Idempotency(멱등성)

같은 요청이 여러 번 들어와도
**결과가 한 번 처리된 것과 같게 유지되는 성질**이다.

예를 들어 주문 이벤트가 중복으로 들어와도
결제가 두 번 일어나면 안 된다.

~~~text
같은 주문 이벤트 여러 번 수신
→ 실제 결제는 한 번만 처리
~~~

### 문제에서 볼 단서

~~~text
중복 이벤트
같은 요청 반복
한 번만 처리
중복 결제 방지
~~~

### 오늘 상태

Q27에서 정답은 맞혔다.

다만 이후에도 문제에서
“재시도”와 “중복 처리 방지”가 같이 나오면
Exponential Backoff와 Idempotency를 구분해서 봐야 한다.

---

# 3. Repartition(재분배)

Glue / Spark 같은 분산 처리에서
데이터를 여러 Partition(파티션)으로 다시 나누는 작업이다.

특정 Worker에 데이터가 몰리는 Data Skew(데이터 편향)가 있을 때
분산을 다시 잡는 데 사용할 수 있다.

~~~text
데이터 몰림
→ Repartition
→ 다시 여러 Partition으로 분배
~~~

### 오늘 상태

Q29에서 정답은 맞혔지만
선택할 때 “1번인가?” 하고 망설였다.

즉:

~~~text
정답 선택
≠ 완전히 정착
~~~

다음에 비슷한 문제에서
**Glue / Spark + Worker 불균형**이 보이면
Data Skew → Repartition 연결을 다시 확인해야 한다.

# 4. Redshift DISTKEY(분산 키)

Amazon Redshift에서 데이터를 여러 Compute Node(컴퓨트 노드)에
어떻게 분산할지 결정하는 기준이다.

특히 JOIN에 자주 사용하는 열을 DISTKEY로 맞추면
노드 사이의 Data Movement(데이터 이동)를 줄이는 데 도움이 될 수 있다.

~~~text
JOIN에 자주 사용하는 Key
→ 같은 기준으로 분산
→ 노드 사이 데이터 이동 감소
~~~

### 오늘 상태

JOIN 시 데이터 이동을 줄이는 문제에서
DISTKEY를 “2?”라고 망설이면서 선택했다.

정답은 맞았지만
확신이 충분했던 상태는 아니었다.

### 다시 볼 것

~~~text
DISTKEY
DISTSTYLE KEY
DISTSTYLE ALL
~~~

특히 ALL과 KEY의 차이는 반복 복습이 필요하다.

민감한 정보가 있는지 탐지하는 데 사용하는 서비스다.

예:

~~~text

민감 데이터
S3 안의 데이터 분류 / 탐지
~~~

기억 포인트:

~~~text

→ Macie
~~~

### 현재 상태

오늘 새로 문제를 통해 다시 접한 범위다.
아직 다른 보안 서비스와 함께 나오면 구분 연습이 필요하다.

# 10. S3 Bucket Policy(버킷 정책)

S3 Bucket에 대한 접근 권한을
Bucket Resource(버킷 리소스) 쪽에서 정의하는 Resource-based Policy(리소스 기반 정책)다.

예:

~~~text
특정 계정만 접근
특정 Principal 허용 / 거부
특정 조건에서만 S3 접근
~~~

### 현재 상태

IAM Policy와 Bucket Policy가 섞일 수 있어
다음 복습에서 다시 구분해야 한다.

~~~text
IAM Policy
→ 사용자 / 역할 쪽 권한

Bucket Policy
→ S3 Bucket 리소스 쪽 권한
~~~

# 12. S3 Versioning(버전 관리)

같은 Key의 객체가 변경되거나 삭제될 때
이전 버전을 남겨 둘 수 있게 하는 기능이다.

~~~text
파일 덮어쓰기
→ 이전 Version 보존 가능
~~~

기억:

~~~text
실수로 덮어씀 / 삭제
→ 이전 버전 복구
→ Versioning
~~~

# 13. S3 Object Lock(객체 잠금)

객체를 일정 기간 동안 삭제하거나 변경하지 못하게 보호하는 기능이다.

특히 WORM(Write Once Read Many) 형태의 보존 요구와 연결된다.

~~~text
규정 준수
삭제 방지
변경 방지
보존 기간
→ Object Lock
~~~

### Versioning과 구분

~~~text
이전 버전 보관
→ Versioning

아예 일정 기간 삭제 / 변경 금지
→ Object Lock
~~~

# 14. AWS DMS(Database Migration Service)

데이터베이스를 AWS로 옮기거나
데이터베이스 간 데이터를 이전하는 데 사용한다.

DB Migration(데이터베이스 이전)

# 15. CDC(Change Data Capture, 변경 데이터 캡처)

처음 한 번 전체 데이터를 옮긴 뒤,
그 이후 발생하는 변경분을 계속 따라가는 방식이다.

~~~text
초기 데이터 이전
+
이후 INSERT / UPDATE / DELETE 변경 추적
→ CDC
~~~

DMS 문제에서
서비스 중단을 줄이며 계속 변경분을 반영해야 할 때 자주 연결된다.

# 16. AWS SCT(Schema Conversion Tool)

서로 다른 Database Engine(데이터베이스 엔진) 사이에서
Schema(스키마)를 변환하는 데 사용하는 도구다.

예:

~~~text
Oracle
→ PostgreSQL

서로 다른 엔진
→ Schema 변환 필요
→ SCT
~~~

### DMS와 SCT 구분

~~~text
실제 데이터 이동
→ DMS

서로 다른 DB 엔진 사이 Schema 변환
→ SCT
~~~

### 현재 상태

오늘 범위에서 함께 봤기 때문에
DMS / CDC / SCT를 한 세트로 다시 보는 것이 필요하다.

온프레미스 스토리지와 AWS 스토리지 사이에서

# 19. AWS Transfer Family

SFTP / FTPS / FTP 같은 전통적인 파일 전송 프로토콜을 사용하면서

FTPS
FTP

# 20. Amazon AppFlow

SaaS 애플리케이션과 AWS 서비스 사이에서
데이터를 이동할 때 사용하는 관리형 서비스다.

# 21. AWS Step Functions

여러 작업을 순서와 조건에 따라 연결하는 Workflow Orchestration(워크플로 오케스트레이션) 서비스다.

~~~text
작업 A
→ 작업 B
→ 조건 분기
→ 실패 시 재시도
~~~

오늘은 특히:

~~~text
Retry
Catch
~~~

를 함께 봤다.

## Retry

실패한 작업을 다시 시도한다.

## Catch

실패가 발생했을 때
다른 처리 경로로 넘긴다.

~~~text
Retry
→ 다시 시도

Catch
→ 실패 처리 경로로 이동
~~~

---

# 25. Apache Iceberg(아파치 아이스버그)

대규모 분석 데이터에서 사용하는 Open Table Format(오픈 테이블 형식)이다.

오늘은 처음 넓게 개념을 접한 단계다.

핵심적으로는
S3 같은 Object Storage 위의 데이터를
테이블처럼 관리하기 쉽게 해 주는 구조로 기억한다.

관련 기능은 이후 다시 세부적으로 확인해야 한다.

~~~text
대규모 분석 데이터
테이블 형식 관리
Schema Evolution
Partition 관리
→ Apache Iceberg
~~~

### 현재 상태

오늘 한 번 본 수준.
아직 세부 기능을 바로 설명할 수 있는 상태로 기록하지 않는다.

| --- | --- |

| Idempotency | 문제에서 회수됨 |

| Redshift DISTKEY | 정답은 맞았지만 확신 부족 |

| Glue DataBrew / Data Quality | 새로 정리, 반복 필요 |

| DMS / CDC / SCT | 세트로 재복습 필요 |
