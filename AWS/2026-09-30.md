# 1. Amazon SNS

SNS는 하나의 메시지를 여러 Subscriber에게 전달하는 서비스다.

```text
Publisher
   ↓
SNS Topic
   ↓
Subscriber 1
Subscriber 2
Subscriber 3
```

핵심:

```text
Pub/Sub
Fan-out
메시지 전달
```

### 내가 이해한 방식

```text
하나의 메시지를 여러 곳에 뿌려준다
→ SNS
```

예:

```text
SNS Topic
├── Email
├── SQS
└── Lambda
```

### 이해 상태

아침 복습에서 SNS 문제를 풀었고  
저녁 5분 복습에서도 2번을 선택해 정답을 맞혔다.

```text
정답
→ O

개념 상태
→ 메시지 전달 / Pub-Sub / Fan-out 역할 이해
```

---

# 2. Amazon EventBridge

EventBridge는 이벤트를 받아 Rule에 따라 Target으로 전달한다.

```text
Event 발생
   ↓
EventBridge
   ↓
Rule 확인
   ↓
Target 실행
```

### 내가 이해한 방식

```text
이벤트를 보고
→ 조건과 맞는지 확인하고
→ 어디로 보낼지 결정
```

핵심:

```text
Event
Rule
Event Pattern
Routing
Target
```

### SNS와 비교

```text
SNS
→ 구독자에게 메시지 전달

EventBridge
→ 이벤트 조건에 따라 Routing
```

### 이해 상태

저녁 5분 복습에서 3번을 선택해 정답을 맞혔다.

```text
정답
→ O

개념 상태
→ SNS와 EventBridge의 역할 차이 이해
```

---

# 3. AWS Step Functions

Step Functions는 여러 작업을 순서대로 연결하고 상태를 관리하는 Workflow 서비스다.

```text
작업 A
   ↓
작업 B
   ↓
작업 C
```

실패나 조건에 따라 분기할 수도 있다.

```text
작업 A
   ↓
성공?
├─ YES → 작업 B
└─ NO  → Retry / 실패 처리
```

핵심:

```text
Workflow
State
순서
분기
Retry
```

### EventBridge와 비교

```text
EventBridge
→ 이벤트를 어디로 보낼지 결정

Step Functions
→ 작업을 어떤 순서로 실행할지 관리
```

### 이해 상태

아침 세션에서 Step Functions 관련 문제를 풀고 설명을 통해 개념을 다시 확인했다.

저녁 5분 복습에서는 4번을 선택해 정답을 맞혔다.

```text
정답
→ O

개념 상태
→ Workflow / 순서 / 상태 / Retry까지 연결해서 이해
```

---

# 4. SNS vs EventBridge vs Step Functions

세 서비스는 모두 여러 AWS 서비스를 연결할 수 있어서 처음에는 비슷해 보일 수 있다.

다시 구분:

```text
SNS
→ 메시지를 여러 구독자에게 전달
→ Pub/Sub
→ Fan-out

EventBridge
→ 이벤트 조건 확인
→ Rule 기반 Routing

Step Functions
→ 여러 작업의 순서와 상태 관리
→ Workflow / Orchestration
```

한 줄로:

```text
SNS
= 메시지 뿌리기

EventBridge
= 이벤트 보고 어디로 보낼지 결정

Step Functions
= 작업 순서와 상태 관리
```

### 이해 상태

```text
세 서비스 구분
→ 이해됨
```

---

# 5. AWS DMS

DMS는 Database Migration Service다.

데이터베이스의 실제 데이터를 다른 데이터베이스로 이전할 때 사용한다.

```text
Source DB
   ↓
  DMS
   ↓
Target DB
```

문제에서 중요하게 본 표현:

```text
Migration
Data
Replication
Minimal Downtime
```

### 내가 이해한 방식

```text
DMS
→ 실제 데이터를 옮긴다
```

예:

```text
On-Premises MySQL
      ↓
     DMS
      ↓
Amazon RDS
```

### 이해 상태

저녁 5분 복습에서 2번을 선택해 정답을 맞혔다.

밤 복습에서도 DMS를 다시 확인했다.

```text
정답
→ O

개념 상태
→ Data Migration 역할 이해
```

# 6. AWS SCT

SCT는 Schema Conversion Tool이다.

서로 다른 Database Engine 사이에서 Schema를 변환할 때 사용한다.

```text
Source DB Schema
      ↓
     SCT
      ↓
Target DB용 Schema
```

예:

```text
Oracle Schema
     ↓
    SCT
     ↓
PostgreSQL용 Schema
```

핵심:

```text
Table 구조
Schema
Database Object
```

### 내가 이해한 방식

```text
SCT
→ 데이터를 옮기는 게 아니라
→ DB 구조를 대상 엔진에 맞게 바꾼다
```

### 이해 상태

저녁 5분 복습에서 1번을 선택했고 정답으로 확인했다.

이 기록에서 SCT를 "확신 부족"으로 처리하면 안 된다.

```text
정답
→ O

개념 상태
→ DMS와 SCT 역할 차이를 구분한 상태
```

밤 세션의 마지막 SCT 문제는 검색된 기록만으로는 사용자 답변까지 확인되지 않았으므로  
그 문제를 근거로 추가적인 오답이나 미이해를 만들어 기록하지 않는다.

---

# 7. DMS vs SCT

둘 다 Database Migration 과정에서 등장할 수 있어서 역할을 분리해서 봐야 한다.

```text
DMS
→ Data 이동

SCT
→ Schema 변환
```

### 내가 외운 방식

```text
DMS = Data
SCT = Schema
```

예:

```text
서로 다른 DB Engine으로 이전

Schema 변환
→ SCT

실제 Data 이동
→ DMS
```

### 이해 상태

```text
DMS
→ 이해됨

SCT
→ 이해됨

둘의 차이
→ 구분 가능
```
