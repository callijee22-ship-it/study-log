# 1. Amazon SNS

## 문제에서 다시 확인한 역할

SNS는 하나의 메시지를  
여러 Subscriber에게 전달하는 서비스다.

```text
Publisher
   ↓
SNS Topic
   ↓
Subscriber 1
Subscriber 2
Subscriber 3
```

핵심은:

```text
Pub/Sub
Fan-out
여러 구독자에게 전달
```

이다.

---

## 내가 이해한 방식

```text
SNS
→ 메시지를 여러 곳에 뿌려주는 서비스
```

예를 들어:

```text
하나의 이벤트 발생
   ↓
SNS Topic
   ↓
Email
SQS
Lambda
```

처럼 여러 대상에게 전달할 수 있다.

---

## EventBridge와 비교

처음에는 SNS와 EventBridge가  
둘 다 “뭔가를 다른 곳으로 보낸다”는 점 때문에 비슷해 보였다.

다시 구분하면:

```text
SNS
→ 구독자에게 메시지 전달

EventBridge
→ 이벤트 조건을 보고 대상 결정
```

---

## 이해 상태

```text
정답 여부
→ 맞음

개념 이해
→ 이해됨
```

단순히 번호를 맞힌 것이 아니라  
SNS가 **구독 기반 메시지 전달 서비스**라는 점까지 구분했다.

---

# 2. Amazon EventBridge

## 기본 개념

EventBridge는 이벤트를 받아서  
Rule에 따라 적절한 Target으로 전달한다.

```text
Event 발생
   ↓
EventBridge
   ↓
Rule 확인
   ↓
Target 실행
```

---

## 내가 이해한 방식

```text
EventBridge
→ 이벤트 내용을 보고
→ 조건과 맞는지 확인하고
→ 어디로 보낼지 결정
```

즉 단순한 메시지 전달보다는

> **이벤트 기반 Routing**

이 핵심이다.

---

## 문제에서 봐야 할 표현

```text
Event
Rule
Event Pattern
Routing
Target
```

이런 표현이 나오면  
EventBridge를 먼저 생각한다.

---

## SNS와 다시 비교

```text
SNS
→ 구독자 중심

EventBridge
→ 이벤트 규칙 중심
```

---

## 이해 상태

```text
정답 여부
→ 맞음

개념 이해
→ 이해됨
```

SNS와 EventBridge의 차이를  
“구독 vs 이벤트 규칙”으로 구분할 수 있었다.

---

# 3. AWS Step Functions

## 기본 개념

Step Functions는 여러 작업을  
순서대로 연결하고 관리하는 Workflow 서비스다.

```text
작업 A
   ↓
작업 B
   ↓
작업 C
```

---

## 오늘 다시 확인한 부분

Step Functions 문제를 풀면서  
다음 세 가지를 확인했다.

```text
A → B → C 순서 실행
State 관리
Retry 처리
```

즉 단순히 서비스 이름만 기억한 것이 아니라  
Step Functions가 작업 흐름 자체를 관리한다는 점을 다시 확인했다.

---

## 내가 이해한 방식

```text
Step Functions
→ 여러 작업의 순서를 정함
→ 현재 상태를 관리함
→ 실패하면 Retry도 처리할 수 있음
```

---

## EventBridge와 비교

```text
EventBridge
→ 이벤트를 어디로 보낼지 결정

Step Functions
→ 작업을 어떤 순서로 실행할지 결정
```

---

## 이해 상태

```text
정답 여부
→ 맞음

개념 이해
→ 비교적 확실하게 이해됨
```

오늘은 단순 정답뿐 아니라

```text
순서
상태
재시도
```

까지 묶어서 이해했다.

---

# 4. SNS / EventBridge / Step Functions 비교

오늘 아침 복습에서  
세 서비스를 다시 구분했다.

```text
SNS
→ Message 전달
→ Pub/Sub
→ Fan-out

EventBridge
→ Event 기반
→ Rule 확인
→ Routing

Step Functions
→ Workflow
→ 순서
→ 상태 관리
→ Retry
```

한 줄로 줄이면:

```text
SNS
= 메시지 뿌리기

EventBridge
= 이벤트 보고 어디로 보낼지 결정

Step Functions
= 작업 순서와 상태 관리
```

---

## 이해 상태

```text
세 서비스 구분
→ 이해됨
```

이날 아침에는 세 문제를 모두 맞혔고  
역할 차이도 다시 설명할 수 있는 상태였다.

---

# 5. AWS DMS

## 기본 개념

DMS는:

```text
Database Migration Service
```

데이터베이스의 실제 데이터를  
다른 데이터베이스로 옮기는 서비스다.

```text
Source DB
   ↓
  DMS
   ↓
Target DB
```

---

## 오늘 문제에서 본 상황

```text
MySQL
   ↓
RDS
```

처럼 데이터베이스를 이전하면서  
Downtime을 줄이는 상황이었다.

---

## 핵심 Keyword

```text
Migration
Data
Replication
Minimal Downtime
```

---

## 내가 이해한 방식

```text
DMS
→ 실제 데이터를 옮긴다
```

---

## 이해 상태

```text
정답 여부
→ 맞음

개념 이해
→ 이해됨
```

문제 상황과 DMS의 역할을 연결할 수 있었다.

---

# 6. AWS SCT

## 기본 개념

SCT는:

```text
Schema Conversion Tool
```

서로 다른 Database Engine 사이에서  
Schema를 변환할 때 사용하는 도구다.

예:

```text
Oracle
   ↓
  SCT
   ↓
PostgreSQL용 Schema
```

---

## 핵심 역할

```text
Table 구조
Schema
Database Object
```

등을 대상 DB에 맞게 변환한다.

---

## 내가 이해한 방식

```text
SCT
→ 데이터를 옮기는 것이 아니라
→ DB 구조를 바꿔주는 도구
```

---

## 이해 상태

```text
정답 여부
→ 맞음

개념 이해
→ 아직 완전히 확실하지는 않음
```

정답은 맞혔지만

```text
1?
```

처럼 확신 없이 선택했다.

즉:

> **정답은 맞았지만 완전히 내 것으로 잡힌 상태는 아니었다.**

---

# 7. DMS vs SCT

이 둘은 Database Migration 문제에서  
같이 등장할 수 있기 때문에 다시 구분했다.

```text
DMS
→ Data 이동

SCT
→ Schema 변환
```

---

## 다시 외운 방식

```text
DMS
→ 데이터

SCT
→ 구조
```

---

## 이해 상태

```text
DMS
→ 이해됨

SCT
→ 역할은 이해했지만 아직 반복 필요
```
